Part I

🥛 MilkPost — the dairy data platform

A dairy-farm app with a small data platform wrapped around it: herd records in, honest metrics and next-week milk forecasts out — on one machine, no cloud AI.

The whole thing in one breath

A farm app, plus a factory that turns its records into answers

MilkPost (internal codename Barnboard) is two things bolted together. A web app a dairy farmer uses daily — log morning/evening milk, track cows on medication, record breedings and sales. And a data platform: an automated "factory" that cleans and models those records into trustworthy numbers and a per-cow milk forecast, then feeds them back to the dashboard.

It runs on one modest machine or a single serverless function, with no GPU and no cloud AI — the entire data-and-models layer is plain standard-library Python. That's deliberate: it runs identically on a farm PC, a cheap server, or a free tier, and the data never leaves the machine.

The product

The dairy app — herd, milk, health, breeding, sales, forecasts, and open data APIs. What a farmer signs into.

The data platform

The pipeline + metrics + models around it. Invisible to the farmer; it makes the dashboard's numbers correct and the forecasts real.

The data · concept + code

Five tables hold the whole farm

Everything the farmer records lives in five plain SQLite tables — the "source of truth" the platform builds on. Here are the two central ones, verbatim from the schema:

barnboard.db — core schema
CREATE TABLE cows (
  id     INTEGER PRIMARY KEY,
  tag    TEXT NOT NULL UNIQUE,        -- ear-tag: the farmer-facing id
  name   TEXT, breed TEXT, dob TEXT,  -- dob = ISO date
  status TEXT NOT NULL DEFAULT 'milking'   -- milking|dry|sold|calf
);

CREATE TABLE milk_logs (
  id       INTEGER PRIMARY KEY,
  cow_id   INTEGER NOT NULL REFERENCES cows(id),
  log_date TEXT NOT NULL,             -- ISO date
  session  TEXT NOT NULL CHECK (session IN ('AM','PM')),
  litres   REAL NOT NULL,
  UNIQUE (cow_id, log_date, session)  -- one row per cow-session-day (upsert)
);
-- plus: treatments, breedings, sales  (the other 3 farm tables)
Privacy line Login accounts, passwords, and sessions live in separate tables that are never exported and never enter the pipeline. Only the five farm tables are ever shared or modelled — personal data and farm data kept strictly apart by design.
The pipeline · concept + code

Medallion: raw → clean → useful

"Medallion" is a naming convention for three quality tiers data passes through, like refining ore. Each layer has one job, and the app never reads a half-processed layer.

Four deterministic stages build it — architect (land+catalogue → bronze), engineer (clean → silver → gold), designer (metrics), analyst (answers). "Deterministic" = run it twice, get byte-identical output. The canonical re-run recipe:

re-run the pipeline (order matters)
python3 tools/make_sources.py          # app DB  ->  5 source CSVs
run_pipeline.py --slug barnboard \
     --sources data-team-sources/*.csv \
     --stages architect,engineer          # ->  bronze, silver, gold
python3 tools/enrich_gold.py             # + agg_milk_cow_daily, breed benchmarks
designer.py --slug barnboard --metrics-dir semantic-metrics   # build metrics
analyst.py  --slug barnboard --ask "avg daily yield per cow"  # answer + receipt
python3 tools/train_models.py            # retrain + backtest + versioned artifact
Re-run order trap Running the later stages alone silently rebuilds the earlier ones and wipes the enrichment. Always: full spine → enrich_gold.py → designer/analyst.
The semantic layer · concept + code

Numbers that carry their own receipt

A semantic layer is one governed dictionary of what each business number means — defined once so it's computed the same way everywhere. Each metric is one JSON file; every answer ships a receipt (definition, version, owner, lineage, exact SQL). A number traces back to the raw logs.

semantic-metrics/price_per_litre.json (v2 override)
{ "metric": "price_per_litre", "version": "v2",
  "aggregation": "ratio",
  "numerator":   "litres_x_price",
  "denominator": "litres",
  "rollups": { "daily": "gold.agg_sales_daily" },
  "unit": "INR/L", "owner": "data-designer" }

-- the guard recomputes ratios from parts, never sums a ratio:
   sum(litres*price_per_litre) / nullif(sum(litres),0)   =>  Rs 42.24   (correct)
   sum(price_per_litre)                                  =>  Rs 422.38  (the bug it caught)
The rule Never sum or average an average. Additive things (totals, counts) may be added up; ratios/averages are recomputed from their parts at whatever level you ask. That single guard makes the classic corruption of farm statistics structurally impossible.
The models · concept + code

Forecasting next week's milk, simply

The "AI" is small and explainable — no neural net, no GPU. Three models: a per-cow 7-day forecast (damped Holt: track level + recent trend, project forward while gently flattening the trend), an anomaly flag (>20% below a cow's own forecast), and a month-end revenue projection.

yield_forecast — damped Holt (the whole model)
fit per cow, over complete cow-days, in order:
  level_0 = y_0 ;  trend_0 = 0
  level_t = a*y_t        + (1-a)*(level_{t-1} + phi*trend_{t-1})
  trend_t = b*(level_t-level_{t-1}) + (1-b)*phi*trend_{t-1}
forecast h days ahead:
  y_hat(h) = max(0, level + (phi^1 + phi^2 + ... + phi^h) * trend)
hyperparameters (stored IN the artifact):  a=0.35  b=0.15  phi=0.92
models/yield_forecast/v1/params.json + hot-swap
{ "model":"yield_forecast", "version":"v1",
  "alpha":0.35, "beta":0.15, "damp":0.92,
  "lineage":["gold.agg_milk_cow_daily"],
  "backtest":{"mae_model":1.247, "mae_naive":1.333},   # must beat naive or the trainer FAILS
  "cows":{ "<id>":{"level":..,"trend":..,"trained_through":".."} } }

# models/yield_forecast/LATEST names the live version.
# The app reads LATEST per request -> publishing a model = update that pointer.
# No restart, no code change.  (verified: v1 -> vtest -> v1 hot-swap)
The data-hygiene rule that made it honest A cow-day with only the morning logged looks like a 50% collapse. The model excludes half-logged days — this halved the forecast error and removed the only false anomaly flag. Data cleaning beat a fancier model.
Open contracts · concept + code

Everything is reachable by machine, on purpose

Stable JSON endpoints let a co-op, a vet's spreadsheet, or a successor system consume — or reclaim — everything. Machines send a feed token and get a clean JSON 401 if it's missing (never an HTML login page).

Auth & sessions · concept + code

Logging in — and the serverless trap that shaped it

Passwords are stored as slow PBKDF2-HMAC-SHA256 hashes (200k iterations) — even the DB can't reveal them. Sessions were the interesting part: on serverless, each request can hit a different throwaway instance with its own empty /tmp DB, so a table-stored session vanished between clicks and looped users back to login.

the two session modes
# password:  password_hash = "<salt_hex>$<dk_hex>"   PBKDF2-HMAC-SHA256, 200_000 iters

# DB-backed (local, default):
#   cookie = 32-byte random token  ->  row in sessions(token, user_id, expires_at)
#   revoke = delete the row (logout-everywhere works)

# Stateless (Vercel, STATELESS_SESSIONS=1):   the cookie IS the session
#   cookie = b64url( "<uid>.<exp>.<sig>" )
#   sig    = HMAC_SHA256( SESSION_SECRET, "<uid>.<exp>" )[:32]
#   any instance verifies it with no shared storage  ->  no login loop
The fix, as a decision Stateless signed cookies removed the login loop. The trade-off — you can't force-expire one before its 30-day life — is accepted for a disposable demo and written down, not left as a surprise. The public PIN gate works the same way: a valid PIN yields a short-lived signed cookie that proxies into the app; wrong PINs are rate-limited.
Deployment · concept + code

Two ways it runs, and why deploys are manual

On this machine every piece runs under pm2 (a process manager that restarts them on reboot, from committed configs). The hosted twin is one Vercel function whose /tmp DB reseeds itself on every cold start — a self-cleaning demo, never real records.

Vercel twin — env + the release ritual
# set before the app imports (api/index.py):
DB_PATH=/tmp/barnboard.db        # ephemeral, self-reseeding
BARNBOARD_SEED=1
STATELESS_SESSIONS=1  +  SESSION_SECRET   # (Vercel encrypted env)
DEMO_LOGIN=demo:farm12345

# RELEASE = two steps.  There is NO git integration:
git push                    # saves + runs CI  (does NOT deploy)
vercel deploy --prod --yes  # actually publishes the change
Remember A git push deploys nothing on this project. Forgetting the vercel deploy is why a change can look "done" but not be live.
Domain, DNS & email · concept + code

The address, and how demo emails send

The public copy lives at milkpost.ajaykongala.online. A domain's DNS is its address book; a "wildcard" answers for any unlisted name. MilkPost rode the wildcard until email records under the same name made the bare subdomain "exist but empty" (DNS rule RFC 4592) and the wildcard stopped answering — the site went dark for minutes.

the zone records that matter (vercel dns add ...)
milkpost                    CNAME  cname.vercel-dns-017.com.     # EXPLICIT record
                                                                 # (never ride the wildcard)
# email trust for Resend, so mail isn't binned as spam:
resend._domainkey.milkpost  TXT    p=MIGf...                     # DKIM  (signature)
send.milkpost               TXT    v=spf1 include:amazonses.com ~all   # SPF (who may send)
send.milkpost               MX 10  feedback-smtp.us-east-1.amazonses.com  # bounces
The standing rule Any hostname that serves something gets its own explicit DNS record — its first "sibling" record silently switches the wildcard off for it. DKIM signs the mail, SPF lists allowed senders; both are published in DNS so receivers trust hello@milkpost.ajaykongala.online.
Part II

🕸️ VaaniMesh — the live translation mesh

Four people, four languages, one conversation. Each speaks their own language and hears everyone else in theirs — speech recognition → translation → speech, per utterance, a few seconds behind.

The whole thing in one breath

A room where everyone speaks their own language

VaaniMesh is a real-time voice-translation mesh for multilingual rooms (Telugu, Bangla, Marathi, Hindi, English). A Telugu speaker talks; the Bangla listener hears Bangla, the Hindi listener hears Hindi — each with a spoken voice and a written caption. Every utterance runs a three-stage pipeline: ASR (speech → text) → MT (translate) → TTS (text → speech).

Speaker consoles

Browser pages that capture your mic and play back translations. Up to five participants.

The relay

An independent server that owns the whole AI pipeline and routes each listener their own version. Nothing about a conversation lives in the browser.

Operator dashboard

A live read-only view of speakers, mic levels, round-trip time, and pipeline latencies.

The pipeline · concept + code

Three paid stages, one pluggable provider

Each utterance passes ASR → MT → TTS. All three run through one provider, chosen per-stage by environment variable — so swapping providers is config, not code. Today that's Sarvam (the OpenRouter key expired; see below).

Honest degradation · concept + code

When the provider dies, the app says so

Because one key can take everything down, the app is built to fail loudly, not silently. The relay's health endpoint reports whether the provider key actually works; the room shows a self-clearing banner when it doesn't; and a watcher emails the owner. None of it guesses — it probes the key.

GET /healthz — provider health drives the UI banner
{ "ok": true,
  "demo_mode": false,
  "provider_ok": true,                       # false + reason when the key is dead
  "provider_reason": "providers configured: sarvam",
  "speakers": 2,
  "latency": { "asr_avg_ms": 900, "mt_avg_ms": 700, ... } }

# server/provider_health.py probes the active provider (TTL-cached).
# The room polls /healthz; provider_ok:false  ->  "translation unavailable" banner.
# tools/health_watch.py emails the owner when provider_ok flips false.
Cost control · concept + code

Zero credits when nobody's listening

A mic left open (or voice-detection firing on background noise) while a speaker is alone would burn provider credits on utterances nobody receives. The relay skips the whole paid pipeline before the ASR call when there are no listeners to translate for.

mesh/relay/processors.py — the idle-cost guard
class ASRStage:
    async def handle(self, frame):
        # no listeners -> nobody to translate for -> skip the PAID pipeline
        # before the ASR call. (MT/TTS already short-circuit on empty targets.)
        if _SKIP_WHEN_ALONE and not self.registry.targets_for(frame.speaker_id):
            frame.suppressed = "no listeners - skipped (idle-cost guard)"
            return
        result = await self.asr.transcribe(frame.wav_bytes)   # only now do we pay
        ...
# verified live: alone speaker -> 0 provider calls; resumes when a listener joins.
Access · concept + code

Joining a room: PIN by email, gated relay

Access is email-first (same pattern as MilkPost): request a PIN, receive it via Resend, then join. Every join — on both the classic app and the mesh relay — is PIN-gated, and wrong attempts are rate-limited. The PIN is unpublished; it only arrives by email.

a speaker join over the relay WebSocket
# request a PIN:  POST /request  { email }  -> Resend emails the PIN + guest login
# then join:
ws  wss://<relay>/ws/speaker
--> { "type":"join", "name":"Ajay", "language":"te-IN", "pin":"<from email>" }
<-- { "type":"joined", "speaker_id":"...", "roster":[...] }      # correct PIN
<-- { "type":"error",  "message":"wrong access PIN" }            # wrong (rate-limited)
Deployment · concept + code

Local relay, public tunnel, Vercel betadoc

Unlike MilkPost, the VaaniMesh app can't run on Vercel — it's a long-lived WebSocket + pipeline server. So the app runs locally under pm2, and only its betadoc is on Vercel. The public /app link is a redirect to a Cloudflare "quick tunnel" into the local relay — but that tunnel's hostname changes on every restart, so a watcher heals the redirect automatically.

betadoc/vercel.json — the /app redirect (auto-healed)
{ "redirects": [
    { "source": "/app",       "destination": "https://<current-tunnel>.trycloudflare.com",       "statusCode": 302 },
    { "source": "/app/:path*","destination": "https://<current-tunnel>.trycloudflare.com/:path*","statusCode": 302 }
] }

# tools/tunnel_sync.sh (pm2: mesh-tunnel-sync) watches the tunnel log;
# on a new hostname it rewrites this file and redeploys the betadoc.
# stable share link stays:  https://vaanimesh.ajaykongala.online/app
The trade-off Quick tunnels are free but fragile (the hostname rotates, occasional edge drops). The durable fix — a named Cloudflare tunnel on a permanent hostname — is deferred because it needs the DNS zone moved to Cloudflare. For a demo, the auto-healer is enough.
