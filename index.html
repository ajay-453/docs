The one-minute model

A pipeline is a checklist a robot runs on every push

Every time you git push, a service spins up a clean, throwaway computer, checks out your exact commit, and runs a fixed list of commands — install, test, maybe deploy. Each command either succeeds (exit code 0) or fails (any non-zero exit code). If every command succeeds, the run is green. If any one fails, the robot stops and the run is red. That green/red mark is stamped back onto your commit and pull request.

Green — passedEvery step exited 0. The commit is verified against everything the pipeline checks. Safe to merge / ship.
Red — failedA step exited non-zero. The robot halted there. Something is broken — the log shows exactly which step and why.
Yellow — runningThe pipeline is still working through the steps. Not a verdict yet, just "in progress."
Grey — skipped / neutralThe step didn't run (a condition wasn't met) or reported no opinion. Neither pass nor fail.

That's the whole traffic light. Green isn't a subjective grade — it's literally "every command in the list returned success."

The vocabulary, decoded

CI and CD are two different promises

People say "CI/CD" as one word, but it's two ideas stacked — and there are actually three, because the second "D" splits.

CI

Continuous Integration

The promise: everyone's changes are merged into the shared branch often, and every merge is automatically built and tested. Break something, and you know within minutes — not at a painful "integration" weeks later.

What it produces: the green/red signal. Nothing ships; it just answers "does this commit still work?"

CD¹

Continuous Delivery

The promise: every green commit is always in a releasable state and can be deployed at the push of a button. A human still decides when to release.

What it produces: a build artifact, ready to go, plus a manual "Deploy" step.

CD²

Continuous Deployment

The promise: every green commit deploys itself to production automatically — no human gate. The pipeline is the release process.

What it produces: code in production, minutes after merge, with no one pressing a button.

In your own stack VaaniMesh does CI only. Its GitHub pipeline runs the tests on every push and reports green/red — but nothing auto-ships, because the app is a live server on your machine, not deployable to Vercel. MilkPost does Continuous Delivery — green commits are releasable, but the actual deploy is a manual vercel deploy --prod you run by hand. Neither does full Continuous Deployment — no green commit reaches production untouched. That's a deliberate, common choice: automate the verification, keep a human on the release trigger.

The steps run top to bottom, and stop at the first failure. So a red run always points at exactly one step — the log ends where it broke. Reading CI is really just reading that one failing step's output.

Gates, not just tests

Your second pipeline guards more than code

The velocity-hub pipeline shows that a CI step can enforce any rule you can express as "exit non-zero if wrong." Three of its gates aren't unit tests at all:

gate 01

Test suite

pytest -q — the 24 Barnboard/MilkPost app tests. The usual correctness gate.

gate 02

Model baseline

train_models.py exits non-zero if the forecast model stops beating the naive baseline. CI refuses to let the ML quietly get worse.

gate 03

Registry drift

check_registry.py fails if a port isn't recorded. This is the gate that emailed you when the 6793 row was duplicated.

That registry-drift email you got wasn't a bug in CI — it was gate 03 doing exactly what it exists to do: it found a real inconsistency (two rows claiming port 6793), exited non-zero, turned the run red, and GitHub emailed you because a run on your default branch failed. You fixed the duplicate, the gate passed, the emails stopped. The red build was the feature.

The mental shift A CI step isn't "run the tests." It's "encode a rule as a command that fails loudly when violated." Tests, linters, type-checkers, security scans, a spreadsheet-consistency check, a "did you update the changelog" check — anything that can exit non-zero can be a gate. Branch protection then makes the green check required: GitHub won't let a red PR merge at all.

Why one problem shows up as many red runs

Three multipliers turned two issues into a wall of red — and understanding them is the whole lesson:

  • A persistent failure re-fails on every push. CI re-runs the full pipeline on each commit. A broken pin or a bad registry row stays broken until you fix it — so every push in between produces its own red run. Ten commits over a broken gate = ten red runs, one bug.
  • A backlog released all at once. The MilkPost commits sat unpushed for ~5 days, then landed in a burst. Each one triggered its own run, so a week's worth of CI fired in a short window — concentrating the failures into a visible cluster instead of spreading them out.
  • Default-branch failures email you. GitHub notifies on failed runs on your main branch. A streak of red on master/main becomes a streak of emails — which is what made it feel like "a lot."
The reassuring read Every one of those red runs was CI working correctly. The pydantic red proved your dependency recipe was wrong before anyone else cloned it; the registry reds caught a real bookkeeping inconsistency and paged you until it was fixed. Zero of them were false alarms. The system was loud because it had genuine things to say — and both were closed with a one-line change.

How to keep the next streak from happening

Push small, push often

The 5-day backlog concentrated the pain. Pushing each change as you finish it means CI verifies one thing at a time — and a failure points at exactly what you just did, not a week of mixed work.

Run the gate locally first

Both failures were reproducible in seconds before pushing: pip install -r requirements.txt in a fresh venv, and python tools/check_registry.py. Running the same command CI runs, locally, catches it before the email does.

Pin to what actually runs

The env-drift class disappears if requirements.txt is generated from the working environment (pip freeze) rather than hand-edited — then the recipe and reality can't diverge.

Deleting runs clears noise, not cause

Removing the failed runs stopped the email clutter — reasonable housekeeping. But the run count was never the problem; the pattern was. Fix the underlying gate and the green returns on its own.

The other way to do it

Jenkins: the same job, self-hosted

GitHub Actions is hosted — GitHub owns the runners, you just write YAML. Jenkins is the older, heavier, more powerful sibling: an automation server you run yourself. Same core idea — a pipeline of stages that go green or red — but you own the machine, the plugins, and the upkeep.

The pieces

  • Controller (the old "master"). The Jenkins server itself: it holds the config, schedules work, and shows the dashboard. You install and maintain it (a VM, a container, a laptop).
  • Agents (the old "nodes"/"slaves"). Worker machines the controller farms builds out to. GitHub's ubuntu-latest runner is the equivalent — except you provision agents yourself.
  • The Jenkinsfile. A pipeline-as-code file in your repo, written in a Groovy-based DSL. It's Jenkins' answer to ci.yml — same purpose, different language.
  • Plugins. Jenkins does almost nothing out of the box; its power (and its maintenance burden) is ~1,800 plugins — Git, Docker, Slack, credentials, the Blue Ocean UI, etc.
  • Triggers. A GitHub webhook pings the Jenkins server on each push, or Jenkins polls the repo on a schedule.

A Jenkinsfile that mirrors your VaaniMesh CI

The same pipeline you already run — but expressed the Jenkins way. Note the shape: pipeline → agent → stages → stage → steps, with a post block for the green/red aftermath.

Jenkinsfile · declarative pipeline
pipeline {
  agent { docker { image 'python:3.12' } }   // where it runs

  triggers { githubPush() }              // webhook on push

  stages {
    stage('Install') {
      steps { sh 'pip install -r requirements.txt' }
    }
    stage('Python tests') {
      steps { sh 'python -m pytest -q' }   // non-zero → red
    }
    stage('JS tests') {
      steps { sh 'node --test "tests/js/*.test.js"' }
    }
  }

  post {
    success { echo 'GREEN ✓ — all stages passed' }
    failure { mail to: 'you@example.com',
               subject: 'Build RED' }   // like GitHub's email
  }
}

Each stage is a labelled box in the dashboard; a sh command that exits non-zero fails its stage and reddens the run — identical semantics to ci.yml, just written in Groovy instead of YAML. The post { failure { … } } block is where you wire up the "build broke" notifications yourself.

Side by side

GitHub Actions vs Jenkins

They solve the same problem. The trade is convenience vs control.

DimensionGitHub Actions (your setup)Jenkins
Who runs the serverGitHub does. Zero infrastructure for you.You do. Install, patch, back up, secure the controller.
Pipeline languageYAML (.github/workflows/*.yml)Groovy DSL (Jenkinsfile)
Runners / agentsHosted VMs on demand (ubuntu-latest); self-hosted optionalAgents you provision and connect yourself
Extending itMarketplace "actions" (uses:)~1,800 plugins you install and version
Cost modelFree minutes for public/small repos; pay for moreFree software; you pay for the machines it runs on
Best whenCode already on GitHub; you want it working todayComplex/legacy/on-prem needs, tight control, air-gapped networks
The green/red signalChecks on the commit & PR; emails on failureStage view / Blue Ocean; you wire up notifications
Which should you use? For VaaniMesh and MilkPost — small repos already on GitHub — GitHub Actions is the right call, and it's what you have. Jenkins earns its keep when you outgrow hosted runners: heavy on-prem builds, strict network isolation, or orchestration too gnarly for YAML. Same concepts transfer directly; you'd mostly be trading a config file's syntax and taking on a server to babysit.

Glossary

Pipeline / Workflow
The whole automated recipe that runs on an event — the list of stages from checkout to (maybe) deploy.
Job
A pipeline runs one or more jobs; each job gets its own fresh runner. Your VaaniMesh workflow has one job, tests.
Step
A single command or action inside a job. Runs in order; the first non-zero exit stops the job.
Stage (Jenkins)
Jenkins' grouping of steps into a labelled, coloured box in the dashboard — "Build", "Test", "Deploy".
Runner / Agent
The machine that executes the work. Hosted (GitHub) or self-provisioned (Jenkins).
Action / Plugin
A reusable, packaged step — actions/checkout on GitHub; a plugin on Jenkins.
Exit code
A command's success signal. 0 = success (green). Anything else = failure (red). The entire traffic light rests on this.
Status check
The green/red mark a pipeline reports back onto a commit or pull request.
Branch protection
A rule that makes a green check required — a red PR can't be merged.
Trigger / Webhook
What starts a run: a push, a PR, a schedule, or a webhook ping from GitHub to a Jenkins server.
Artifact
A file a pipeline produces and keeps — a build output, a test report, a packaged release.
Gate
Any step whose job is to fail the build when a rule is violated — tests, a model baseline, a registry check.
